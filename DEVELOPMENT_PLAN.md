# DEVELOPMENT_PLAN.md — «Контроль металла»

Ориентир по итерациям. Уточняется по факту, но порядок и критерии выхода — обязательны: каждая итерация закрывается только при выполнении всех exit-критериев.

После каждой итерации без исключений: typecheck, lint, unit/integration-тесты, production build, проверка Prisma-миграций, `git diff`-ревью, удаление debug-кода, обновление ARCHITECTURE.md/этого файла при отклонениях от плана, отчёт (что сделано / файлы / тесты / техдолг / что дальше).

## Iteration 1 — Foundation

- Инициализация Next.js (App Router, TS strict), `docker-compose.dev.yml` с отдельной dev-БД PostgreSQL.
- `prisma/schema.prisma` по проекту из ARCHITECTURE.md §4, первая миграция, `seed.ts` с минимальными справочными данными для разработки.
- `.env.example`, `src/lib/config.ts` — валидация env при старте (падать сразу, а не на первом запросе).
- `Dockerfile`, `docker-compose.dev.yml`.
- `GET /api/health`, `GET /api/health/ready` (проверка соединения с БД).
- Базовый error handler, security-заголовки (`next.config.js`), логирование.
- ESLint/Prettier/Vitest настроены и проходят на пустом каркасе.

**Exit:** `docker compose up` поднимает приложение + БД с нуля, `/api/health` и `/api/health/ready` отвечают 200, `prisma migrate deploy` проходит на чистой БД, seed выполняется идемпотентно.

## Iteration 2 — Admin и справочники

**Exit:** можно залогиниться, разлогиниться, попытка зайти в `/admin/*` без сессии редиректит на login; все 4 справочника управляются через UI; деактивированная запись не отдаётся как активная нигде в системе.

## Iteration 4 — Excel-импорт ✅ (материализовано также `material-normalization.ts`, см. ниже)

- `src/lib/material-normalization.ts` — оба алгоритма (форматная для RAL/толщины, alias-lookup для производителя/покрытия) + единая `validateMaterialRow`. Изначально план относил этот модуль к Iteration 5, но Excel-импорту он нужен раньше, и оба потребителя (Excel-строка, позже `/check`) по дизайну используют один и тот же модуль (ARCHITECTURE.md §5) — решение сдвинуть построение сюда зафиксировано в Decision Log (ARCHITECTURE.md §15, 2026-08-12). Iteration 5 просто переиспользует его.
- `src/lib/excel/`: `parse.ts` (чтение листа `Import`, лимит строк), `template.ts` (генерация `Import`+`Reference`) — на `exceljs`, не на изначально предполагавшемся `xlsx`/SheetJS (npm-пакет `xlsx` не обновлялся с 2022 — см. Decision Log).
- `POST /api/admin/import/parse` → превью (итоги + ошибки по строкам).
- `POST /api/admin/import/confirm` → создание `Coil` (`createMany`, одной операцией), повторная валидация ссылок на справочники (сервер не хранит состояние между parse/confirm), идемпотентный ключ (in-memory кэш с TTL) — отчёт.
- Генерация шаблона (`GET /api/admin/export/excel-template`) с листами `Import` + `Reference` из текущих справочников.
- Лимит строк за импорт (5000), защита от повторного нажатия (client-side блокировка кнопки + idempotency key).

**Exit:** файл с валидными и невалидными строками → превью верно классифицирует каждую строку с номером; подтверждение создаёт только валидные; повторный клик на confirm не дублирует импорт; шаблон скачивается и содержит актуальные значения справочников.

## Iteration 8 — Печать QR ⚠️ реализовано и проверено декодированием; проверка настоящей бумажной печати реальной камерой — ОТКРЫТА

- Генерация QR — `qrcode@1.5.4`, серверный SVG (`src/lib/qr/coil-passport.ts`), встроен прямо в SSR HTML страницы паспорта (`dangerouslySetInnerHTML` над собственным серверным выводом, не пользовательским вводом). `errorCorrectionLevel: "H"` (максимальный, 30%) — печатная этикетка в цеху подвержена загрязнению/бликам сильнее экрана.
- QR кодирует ровно то же самое, что принимает сканер рулона: абсолютную ссылку `${NEXT_PUBLIC_APP_URL}/coil/:id` (`buildCoilPublicUrl`), без каких-либо дополнительных параметров — симметрично `parseCoilScanUrl` (ARCHITECTURE.md §10).
- Паспорт рулона (QR + RAL/толщина/производитель/покрытие/id) — `/admin/coils/[id]/print`, защищён admin-авторизацией (по факту реализации: не отдельная публичная страница, как можно было понять из первоначального плана — решение и обоснование см. Decision Log ARCHITECTURE.md §15). Ссылка «Печать» рядом с «Открыть» в списке рулонов (`CoilsManager`).
- Print view — `window.print()` (клиентская кнопка `PrintButton`) + `@media print` в `globals.css` (скрывает admin-навигацию через класс `.no-print`, доступный любой странице). Серверный PDF не потребовался — вёрстки в одну карточку хватило.

**Проверено:** unit-тест `tests/unit/coil-passport.test.ts` — включает настоящий round-trip: `qrcode` кодирует ссылку → PNG (тем же движком кодирования, что и SVG в паспорте) → `pngjs` читает пиксели → `jsqr` раскодирует изображение обратно в текст → результат сверяется с исходной ссылкой И проходит `parseCoilScanUrl` (тот же валидатор, что использует сканер рулона на `/scan/coil`). Это не мок — честная декодировка сгенерированного изображения. Также вручную открыт `/admin/coils/[id]/print` в dev-стеке (реальный залогиненный запрос) — страница отдаёт корректный SVG, QR визуально проверен (сгенерирован PNG той же ссылки, просмотрен).

**НЕ проверено — открытый пробел (как и камера в Iteration 6, офлайн в Iteration 7 — это отдельный, третий пробел того же рода):** физическая печать на настоящем принтере и считывание получившейся бумажной этикетки обычной камерой телефона в реальных условиях (может выявить проблемы, которых нет в цифровом round-trip — низкое DPI принтера, размер этикетки, качество бумаги/тонера, блики).

**Exit:** цифровой round-trip (кодирование → печатный движок → декодирование → валидация тем же кодом, что использует сканер) подтверждён автотестом; финальное подтверждение «напечатанный на бумаге QR сканируется телефоном» остаётся сделать вручную.
