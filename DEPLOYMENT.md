# DEPLOYMENT.md — деплой на Timeweb Cloud

## Топология

```
Интернет (HTTPS)
      │
      ▼
Timeweb reverse-proxy / сертификат
      │
      ▼
Docker-контейнер: Next.js (standalone build), один процесс
      │
      ▼
Managed PostgreSQL (Timeweb) — PROD-инстанс
```

Отдельно, физически изолированно:

```
Разработка (локально / staging)
      │
      ▼
Managed PostgreSQL (Timeweb) — DEV-инстанс, отдельные креды и адрес
```

## Почему dev и prod — разные инстансы БД, а не одна БД с ветками

Timeweb Cloud PostgreSQL не имеет фичи «веток БД по требованию» (в отличие от Neon, использовавшегося в прошлом проекте — там смешение dev/prod уже случалось), которая раньше давала дешёвую изоляцию dev/prod на одной физической базе. Без неё переключение между dev и prod на одной базе — источник риска смешения данных. Поэтому изоляция строится на двух независимых уровнях (полное описание и обоснование — ARCHITECTURE.md §11.1, здесь — что это значит для процесса деплоя):

- **Физически** — заводится **отдельный** managed PostgreSQL-инстанс Timeweb для dev с Iteration 1 (не позже), с собственным хостом и учётными данными, а не отдельная БД/схема на том же инстансе, что и prod. `DATABASE_URL` для dev и prod хранятся в разных секретах, никогда не в одном файле с закомментированной альтернативой.
- **Программно** — при первом создании каждого инстанса вручную выполняется одноразовый seed, записывающий маркер `EnvironmentGuard.env` (`"development"` или `"production"`) прямо в эту БД. Каждый запуск приложения передаёт `APP_ENV` и на старте сверяет его с этим маркером — при несовпадении процесс не стартует (детали — ARCHITECTURE.md §11.1). Это ловит именно тот класс ошибок, который физическое разделение само по себе не ловит: человек скопировал не тот `DATABASE_URL` в переменные деплоя.
- Для локальной песочницы разработчика — либо собственный Docker Postgres (`docker-compose.dev.yml`, с собственным `EnvironmentGuard.env = "development"` в seed), либо дамп dev-инстанса (`pg_dump`/`pg_restore`) при необходимости повторяемого состояния — никогда дамп/восстановление из prod в dev-направлении без явного обезличивания (в V1 нет персональных данных, но правило фиксируется как процессное на будущее).

## Docker

- Production-образ — многоступенчатая сборка (`next build --webpack` с `output: "standalone"`), финальный слой — минимальный Node runtime + собранное приложение, без dev-зависимостей. `--webpack` обязателен, не косметика: Next.js 16 по умолчанию собирает `next build` через Turbopack, а `@serwist/next` (service worker, ARCHITECTURE.md §9) подключается только через webpack — без флага `public/sw.js` молча не генерируется (Decision Log ARCHITECTURE.md §15).
- Миграции применяются **до** старта приложения: entrypoint-скрипт запускает `prisma migrate deploy`, затем стартует Next.js сервер. Если миграция падает — контейнер не поднимается (fail closed на уровне деплоя тоже).
- **Известная особенность №3 (найдена и исправлена в Iteration 7, не PWA-специфична):** `Dockerfile` изначально точечно копировал `node_modules/.bin/prisma`/`node_modules/prisma`/`node_modules/@prisma` в runner-образ — при первом реальном прогоне `entrypoint.sh` в собранном образе (до этого не проверялось сквозным прогоном, только `npm run build`) `prisma migrate deploy` падал с `ENOENT: .../node_modules/.bin/prisma_schema_build_bg.wasm`: копирование одиночного файла-symlink через `COPY --from` разыменовывает его в обычный файл, ломая относительные пути внутри CLI, плюс не хватало транзитивных зависимостей CLI (`effect`), которые npm поднимает в корень `node_modules`. Исправлено отдельной стадией `prod-deps` (`npm ci --omit=dev`) и копированием её `node_modules` в runner **целиком одной командой** — подробности и обоснование в Decision Log ARCHITECTURE.md §15. Урок на будущее: `npm run build` зелёный не значит, что `entrypoint.sh` в собранном образе действительно стартует — перед объявлением деплой-итерации готовой нужен хотя бы один реальный прогон `docker build --target runner` + запуск контейнера против тестовой БД.
- `docker-compose.dev.yml` — Next.js в dev-режиме + Postgres-контейнер для локальной разработки, не используется в проде.
- `docker-compose.dev.yml` держит `node_modules` в отдельном именованном volume (`app-node-modules`), не в bind-mount с хоста — иначе Windows-хост подменял бы Linux-нативные бинарники (например, `@node-rs/argon2`) несовместимыми. **Исправлено (было известной особенностью с ручным обходом до Iteration 5):** команда контейнера начинается с `npm install`, который синхронизирует volume с текущим `package.json`/`package-lock.json` при каждом старте (быстрый no-op, если ничего не изменилось) — добавление зависимости на хосте теперь подхватывается обычным `docker compose up` без `docker volume rm`. До этого исправления баг наступал минимум 3 раза подряд в разных итерациях (Iteration 2 `@node-rs/argon2`, Iteration 4 `exceljs`, Iteration 5 `idb-keyval`) — каждый раз чинился вручную одноразово, что и подсказало сделать это частью самого compose-файла, а не держать как процессную заметку.
- **Известная особенность №2 (dev-only баг роутинга Next.js 16.3.0, не проблема кэша — см. уточнение ниже):** в dev-режиме (и под Turbopack, и под webpack — проверено обоими) маршруты вида `/api/admin/{resource}/[id]/{action}/route.ts` (например `deactivate`/`restore`) иногда отвечают 404 вместо ожидаемого статуса, при этом `[id]/route.ts` (без дополнительного статического сегмента) работает нормально. Воспроизведено и локализовано: причина — не устаревший кэш (первая версия этой заметки ошибочно называла причиной `app-next-cache`; `docker volume rm` иногда «помогал» случайно, не по сути), а сам dev-сервер Next.js 16.3.0, у которого ломается регистрация маршрутов при **нескольких (5+) параллельных ресурсах с одинаковой вложенной формой** `[id]/статический-сегмент/route.ts` (у нас — `colors`/`thicknesses`/`manufacturers`/`coatings`/`coils`, у каждого `deactivate`+`restore` одинаковой формы). Подтверждено экспериментально: изолированный тестовый маршрут той же формы по одному пути работал всегда; баг проявлялся непредсказуемо в зависимости от того, сколько одинаковых по форме маршрутов уже зарегистрировано, и не зависел от кэша, бандлера (Turbopack/webpack) или содержимого хендлера.
  - **Production не затронут** — явно проверено: `next build && next start` (или полный prod-Docker-путь) корректно отдаёт 200/410/404 на тех же URL, где dev 404-ил. Это подтверждено для `colors/[id]/deactivate`, `colors/[id]/restore`, `coils/[id]/deactivate` в рамках Iteration 3.
  - **Что делать, если это увидели в dev:** не тратить время на поиск бага в коде хендлера — сначала перепроверить тот же запрос против `next build && next start` (или `Dockerfile` target `builder`+`runner`). Если там всё работает — это тот самый dev-only баг, а не регрессия. Практических стопроцентных workaround'ов для dev не найдено (ни `docker volume rm app-next-cache`, ни рестарт контейнера не гарантируют исправление); единственное, что надёжно помогало в наблюдаемых случаях — удаление/изменение состава файлов маршрутов провоцировало пересборку route-manifest, после чего проблема пропадала сама. Не блокирует работу — это неудобство локальной разработки, не дефект приложения.

## Переменные окружения (production)

Перечисляются (без значений) в `.env.example`, обязательные для прод-деплоя:

- `DATABASE_URL` — строка подключения к prod PostgreSQL.
- `APP_ENV=production` — независимо от `NODE_ENV`, используется исключительно для сверки с `EnvironmentGuard` в БД (ARCHITECTURE.md §11.1). Для dev-окружения (локально или staging) — `APP_ENV=development`.
- `SESSION_COOKIE_SECRET` — секрет для подписи/шифрования служебных данных сессии (не пароль admin, отдельный секрет уровня приложения).
- `NEXT_PUBLIC_APP_URL` — публичный HTTPS-домен (используется для генерации абсолютных URL в QR-кодах рулонов и для проверки `Origin`/`Referer` при CSRF-защите admin-эндпоинтов).
- `NODE_ENV=production`.

`src/lib/config.ts` валидирует полный набор при старте процесса — отсутствие обязательной переменной останавливает запуск с понятной ошибкой, а не падение на первом запросе от пользователя. Проверка `APP_ENV` против `EnvironmentGuard.env` выполняется здесь же, до `prisma migrate deploy` — несовпадение останавливает запуск контейнера целиком (см. процесс деплоя ниже).

## HTTPS

Обязателен на проде без исключений — нужен и для доступа к камере через `getUserMedia` (браузеры требуют защищённый контекст), и для корректной работы QR-кодов, которые сканирует обычная камера телефона. Сертификат и терминация TLS — на уровне Timeweb reverse-proxy перед контейнером; сам Next.js-процесс внутри контейнера работает по HTTP на внутренней сети.

Для локальной разработки, где нужна проверка камеры (Iteration 6+), — `mkcert` для локального доверенного сертификата, либо тестирование прямо на задеплоенном staging-домене с телефона (второй вариант предпочтителен для реальной проверки iOS Safari — эмуляция локального HTTPS не гарантирует идентичное поведение).

## Health checks

- `GET /api/health` — liveness, 200 если процесс жив.
- `GET /api/health/ready` — readiness, 200 только если есть рабочее соединение с БД, иначе 503. Используется платформой/оркестрацией для решения «готов ли контейнер принимать трафик».

**Известная особенность №4 (найдена и исправлена при реальном деплое на Timeweb Cloud App Platform, Iteration 9): standalone-сервер Next.js слушал недоступный адрес.** Контейнер стартовал и логировал `✓ Ready`, `EnvironmentGuard: проверка пройдена`, но платформенный healthcheck никогда не проходил, контейнер бесконечно перезапускался, деплой падал через 3 минуты по таймауту. Причина видна в самом баннере запуска: `- Network: http://<container-id>:3000` вместо ожидаемого `0.0.0.0`. `sh` (ash/dash в `node:24-alpine`), через который `entrypoint.sh` запускает `node server.js`, автоматически экспортирует переменную `HOSTNAME` = имя хоста контейнера (в Docker это его container ID) — а сгенерированный Next.js `server.js` слушает на `process.env.HOSTNAME || '0.0.0.0'`, то есть из-за автоэкспорта shell'а никогда не попадает в дефолт `0.0.0.0` и слушает только на адресе, в который резолвится хост контейнера — это, как правило, НЕ включает loopback (`127.0.0.1`), поэтому ломает как внешние подключения, так и `curl http://localhost:PORT` изнутри самого контейнера (см. особенность №5 — на практике оба бага перекрывали друг друга, и по логам было не различить, какой из них действует). **Исправлено** — `docker/entrypoint.sh` явно переопределяет `export HOSTNAME=0.0.0.0` непосредственно перед `exec node server.js`. Это общая особенность Next.js standalone в Docker, не специфичная для Timeweb.

**Известная особенность №5 (найдена по ответу поддержки Timeweb, Iteration 9): healthcheck App Platform выполняется как `docker exec <container> curl ...` внутри контейнера, а не внешним HTTP-запросом.** Базовый образ `node:24-alpine` не содержит `curl` — без него health-проверка не может выполниться в принципе (`curl: not found`), деплой никогда не завершается успехом независимо от того, насколько здоров сам процесс. Это единственная платформо-специфичная часть: другие платформы, делающие healthcheck внешним HTTP-запросом извне контейнера, эту проблему не поймали бы, но поймали бы особенность №4 (это и произошло при локальной проверке — `docker run -p` + `curl` с хоста прекрасно проходил ещё до того, как всплыла эта особенность). **Исправлено** — `RUN apk add --no-cache curl` в `runner`-стадии `Dockerfile`. Проверено локально: `docker exec <container> curl http://localhost:3000/api/health` отдаёт `200` только после добавления пакета. Урок: воспроизведение локальным `docker run` + внешний `curl` не гарантирует идентичность тому, что реально делает конкретная платформа — если есть возможность узнать точный механизм healthcheck (у Timeweb — через поддержку), стоит явно это проверить (`docker exec ... curl`), а не полагаться на предположение о внешнем HTTP-пробе.

## Процесс деплоя (Iteration 9)

1. Сборка production-образа из тега/ветки.
2. Старт контейнера → `config.ts` проверяет `APP_ENV` против `EnvironmentGuard.env` на БД из `DATABASE_URL`. Несовпадение — контейнер падает сразу, миграции не запускаются, деплой считается неудавшимся (см. ARCHITECTURE.md §11.1).
3. Прогон миграций на prod-БД (`prisma migrate deploy`) — не `db push`, чтобы миграции были версионируемы и воспроизводимы.
4. Запуск нового контейнера, проверка `/api/health/ready`.
5. Переключение трафика (если Timeweb поддерживает blue/green — использовать; если нет — короткое окно недоступности допустимо для V1, не оптимизируется отдельно).

## Логирование

Structured logging в stdout/stderr контейнера (JSON-формат для машинного разбора) — Timeweb собирает логи с контейнера штатно, отдельная система логирования не разворачивается в V1.

## Резервное копирование

Регулярные бэкапы prod PostgreSQL — через штатный механизм Timeweb Managed PostgreSQL (если предоставляется платформой) либо `pg_dump` по расписанию как fallback. Частота и глубина хранения бэкапов — уточнить лимиты тарифа Timeweb на этапе Iteration 9, зафиксировать здесь по факту.
