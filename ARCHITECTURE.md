# ARCHITECTURE.md — «Контроль металла»

Статус: архитектурный проход завершён, реализация не начата. Этот документ фиксирует решения, чтобы к ним не возвращаться повторно без явной причины.

## 1. Цель и границы системы

Единственная задача: сравнить материал, требуемый по накладной (4 параметра из QR, сгенерированного 1С), с материалом фактически отсканированного рулона. Результат — бинарный: МОЖНО / СТОП.

Явно НЕ входит в систему: партии, вес, длина, площадь, остатки, поставщики, склады, заказы, накладные как сущность, клиенты, цены, станки, профили изделий, история проверок (V1), push, чат, AI, множественные роли, нативное приложение, публикация в сторах, HMAC-подпись `/check`-URL, GraphQL.

Полный список исключений: см. §12.

## 2. Структура проекта: один Next.js-проект

**Решение:** единый Next.js-проект (App Router). Route Handlers (`src/app/api/**`) — API-слой поверх Prisma. Публичные страницы (`/`, `/check`, `/coil/:id`) — Server Components, читающие Prisma напрямую при SSR, без похода через собственный HTTP API. Admin-часть — под `/admin/*`, защищена middleware/layout-guard.

**Важное исключение из этого правила:** страница `/coil/:id` в режиме сравнения (когда есть активное требование) — это НЕ SSR-вердикт. Итоговый МОЖНО/СТОП всегда вычисляется client-side компонентом через `fetch('/api/coil/:id', { cache: 'no-store' })` после монтирования, а не сервером при рендере HTML-страницы. Причина — §9: service worker кэширует HTML app shell, и если бы вердикт вычислялся на сервере и попадал в закэшированный HTML, повторное офлайн-открытие той же ссылки могло бы показать устаревший вердикт по деактивированному/изменённому рулону — прямое нарушение fail closed. SSR для `/coil/:id` используется только для read-only карточки (нет активного требования) — там нет вердикта, значит нет риска протухания.

**Почему не web+api раздельно:** единственный потребитель API — тот же фронтенд; стороннего клиента нет и не запланировано. Раздельные сервисы добавили бы: второй Docker-образ, сетевой вызов между сервисами, дублирование валидации, отдельный CORS-конфиг — без компенсирующей выгоды при таком объёме бизнес-логики (сравнение 4 полей). Если в будущем появится внешний потребитель API — Route Handlers уже физически изолированы в `app/api/*` и выносятся без переписывания бизнес-логики (она живёт в `src/lib/`, а не в обработчиках маршрутов).

Приоритет №10 ТЗ («минимум лишней архитектуры») — прямой аргумент в пользу этого решения.

### 4.1 Толщина — `Int` в сотых мм, не `Float`, не `Decimal`

`Float` даёт риск ошибок сравнения из-за двоичного представления (`0.1 + 0.2 !== 0.3`-класс проблем) — недопустимо там, где решение МОЖНО/СТОП зависит от точного равенства. `Decimal` в Prisma сериализуется в JSON как строка и требует отдельной библиотеки на клиенте для арифметики/сравнения — накладные расходы без выгоды, поскольку нам не нужна произвольная точность, только целые сотые миллиметра. Поэтому канон — `Int` (`valueHundredths`), например `50` = 0,50 мм. `displayName` хранит готовую человекочитаемую строку с запятой («0,50 мм»), не выводится из числа на лету, чтобы формат вывода был предсказуем и настраивался администратором отдельно от значения.

### 4.2 `id` — `cuid()`, непредсказуемый, не последовательный

Удовлетворяет требованию раздела 7: нельзя перебором URL найти существующие рулоны или подделать `/coil/:id` инкрементом.

### 4.3 `Coil` ссылается на справочники по FK, не хранит копии значений

Гарантирует на уровне схемы, что рулон физически не может иметь неканоническое/устаревшее значение характеристики — invalid state непредставим.

### 4.4 `aliases` — `String[]` на самой записи, не отдельная таблица

`Manufacturer`/`Coating` — маленькие справочники (единицы-десятки записей), alias-список на запись — единицы вариантов. Отдельная join-таблица добавила бы JOIN на каждый lookup без реальной пользы на таком объёме. Если в будущем понадобится алиасам собственный жизненный цикл (кто добавил, когда) — миграция на таблицу тривиальна.

### 4.5 Без уникального constraint на комбинацию 4 характеристик у `Coil`

Прямое требование раздела 24 — несколько физических рулонов с одинаковыми характеристиками нормальны, у каждого свой QR.

### 4.6 `EnvironmentGuard` — техническая защита от смешения dev/prod

Не бизнес-сущность, не часть модели предметной области — однострочная таблица-маркер, которая физически живёт внутри конкретной БД и хранит, каким окружением эта БД является. Используется в паре с `APP_ENV` (см. §11.1) как guard-проверка при старте приложения: если значение в таблице не совпадает с ожиданием — приложение не стартует. Механизм подробно — §11.1.

## 5. Нормализация — единый модуль, два алгоритма

`src/lib/material-normalization.ts` — единственное место, где строковые/числовые значения из `/check`-параметров или Excel превращаются в канонические ссылки на записи справочников. Два разных алгоритма внутри одного модуля (см. §13 исходного ТЗ), намеренно не унифицированные:

- **RAL и толщина** — форматная нормализация: убрать пробелы, `"мм"`, привести запятую к точке, привести к каноническому виду (`"0,50"` / `"0.50"` / `"0.5"` → `50` сотых мм). У этих справочников нет `aliases` — не нужны, у формата конечное число вариаций, которые разбираются кодом, а не ручной регистрацией.
- **Производитель и покрытие** — точный lookup по `code` (case-insensitive) либо по элементу `aliases`. Никакого fuzzy/similarity-сопоставления. Не найдено — не «предположим ближайшее», а СТОП/«ОШИБКА В НАКЛАДНОЙ».

Любое значение, не прошедшее нормализацию — не угадывается, always fail closed.

## 6. `ActiveMaterialRequirement` — жизненный цикл и хранилище

Хранится **в браузере**, никогда на сервере (сервер не хранит состояние текущей проверки — это состояние конкретного устройства работника, не бизнес-сущность).

Хранилище: **IndexedDB** через `idb-keyval`, не `localStorage`. Причина: `localStorage` синхронный и может быть агрессивнее вытеснен при memory pressure на слабых Android-телефонах в фоновой/свёрнутой вкладке; IndexedDB — асинхронное, обычно с более высоким приоритетом сохранности у браузеров, и естественно поддерживает будущее поле TTL (`expiresAt: number | null`) без миграции схемы хранения (просто новое опциональное поле в объекте).

Форма объекта:
```ts
type ActiveMaterialRequirement = {
  ral: string;            // canonical code, e.g. "7024"
  thicknessHundredths: number;
  manufacturer: string;   // canonical code, upper-case
  coating: string;        // canonical code, upper-case
  createdAt: string;      // ISO
  expiresAt: string | null; // задел на будущее (не обязателен для V1)
};
```

Поведение при новом `/check` поверх незавершённого требования — модальное подтверждение с показом текущего требования (раздел 6 ТЗ), не молчаливая перезапись.

## 7. Excel-импорт — архитектура потока

**Решение: без промежуточной таблицы в БД. Сервер не хранит состояние между parse и confirm — держатель состояния в этом промежутке — браузер admin'а, а не сервер.** Явная схема:

1. Admin загружает `.xlsx` → `POST /api/admin/import/parse` (multipart).
2. Сервер парсит (`exceljs` — см. §14 п.12 про выбор библиотеки), прогоняет через `material-normalization`, валидирует существование/активность справочных записей. Ничего не сохраняет — ни в БД, ни в серверной памяти/сессии. Ответ отправлен — сервер немедленно забыл про этот импорт.
3. Ответ — JSON превью: итоги (всего/корректных/с ошибками) + провалидированный набор строк (с уже разрешёнными `colorId`/`thicknessId`/`manufacturerId`/`coatingId`) + ошибки по номерам строк.
4. **Держатель состояния между шагами — состояние React-компонента admin-страницы импорта в браузере** (не `localStorage`/`sessionStorage` — обычный component state достаточен, т.к. состояние нужно только пока открыта эта конкретная вкладка импорта; если admin перезагрузит страницу до подтверждения — предпросмотр теряется и нужно загрузить файл заново, это осознанно приемлемо, а не потерянная функциональность). **Никакого токена и TTL нет и не нужно** — нет server-side состояния, которое могло бы «протухнуть» по времени.
5. Admin подтверждает → клиент отправляет **тот же набор валидных строк** на `POST /api/admin/import/confirm`.
6. **Сервер трактует этот payload как недоверенный ввод, не как формальность.** На confirm выполняется **повторная валидация** каждой строки — те же проверки существования и активности `colorId`/`thicknessId`/`manufacturerId`/`coatingId`, что и на шаге parse, — потому что между parse и confirm могло пройти произвольное время, за которое admin (в другой вкладке) или кто-то другой мог деактивировать одну из справочных записей. Строка, не прошедшая повторную валидацию на confirm, исключается из импорта и попадает в `skipped` итогового отчёта — она не откатывает весь импорт, но и не создаётся вслепую. Только строки, прошедшие обе проверки (parse и confirm), создают `Coil`-записи — одной транзакцией.
7. Идемпотентный ключ на `confirm` (см. API_CONTRACT.md) защищает от другого риска — двойного клика/повторной отправки одного и того же запроса, а не от протухания данных; это два разных механизма защиты, оба нужны одновременно. Реализация — in-memory кэш `idempotencyKey → результат` с TTL 1 час (`src/lib/admin/import-idempotency.ts`, тот же паттерн, что rate-limit на логине — один инстанс приложения, Redis не нужен для объёма единичных admin-импортов). Повторный запрос с тем же ключом отдаёт закэшированный результат, не создавая записи заново.

Почему без staging-таблицы: это избежало бы ещё одной сущности ради двух шагов одного действия; данные небольшие (сотни–тысячи строк), roundtrip через клиента дешевле и проще, чем управлять жизненным циклом временных записей (когда чистить, что если admin не подтвердил). Повторная валидация на confirm закрывает единственный риск, который staging-таблица с TTL решала бы иначе (протухание) — здесь он решается не временем жизни записи, а тем, что источник истины (справочники в БД) перепроверяется заново при каждом реальном использовании данных, а не один раз на предпросмотре. Защита от объёма: лимит строк за импорт (5000, настраиваемо) — проверяется уже на шаге `parse`.

Подробности формата и пользовательского потока — `EXCEL_IMPORT.md`.

## 8. Security model

- Хеширование паролей: **`@node-rs/argon2`** — Rust-биндинги с готовыми прекомпилированными бинарниками под Windows и Linux; в отличие от `node-argon2` (node-gyp, нативная компиляция) не требует тулчейна сборки ни в dev на Windows, ни в Docker-образе. Более современный и безопасный выбор, чем `bcryptjs`, без цены в виде сложной сборки.
- Сессии администратора: **DB-backed**, модель `AdminSession`. Токен сессии — непредсказуемая строка в httpOnly, `Secure`, `SameSite=Lax` cookie. Явно НЕ JWT-в-cookie: при 1–2 admin-аккаунтах и низкой частоте логинов DB-сессия даёт бесплатную мгновенную отзываемость (деактивировал `AdminUser.active` → все его сессии недействительны при следующей проверке), тогда как отзыв JWT потребовал бы собственного blacklist — то есть той же таблицы, но сложнее.
- CSRF: `SameSite=Lax` закрывает базовый случай; на мутирующих admin-эндпоинтах дополнительно проверяется `Origin`/`Referer` совпадающий с собственным доменом.
- Rate limiting на `POST /api/admin/login` — in-memory (единственный инстанс приложения, Redis не нужен).
- Security-заголовки через `next.config.js` `headers()`: CSP, `Permissions-Policy: camera=(self)`, `X-Frame-Options: DENY`, `Strict-Transport-Security`, `Referrer-Policy: same-origin`.
- Секреты — только через env-переменные, `.env.example` перечисляет обязательные без значений.

## 9. PWA / офлайн-стратегия ✅ Iteration 7 — реализовано; проверка на реальном устройстве (авиарежим) ОТКРЫТА

Service worker через `serwist` (актуальный, поддерживаемый форк workbox-подхода под Next.js App Router).

**Инструмент:** `serwist@9.5.12` + `@serwist/next@9.5.12` — генерирует и регистрирует service worker на основе декларативной конфигурации `runtimeCaching` в `next.config.ts`/`src/app/sw.ts`, без ручного написания низкоуровневого SW-кода.

**Собирается только в production build, не в dev.** `@serwist/next` подключается через `webpack()`-хук `next.config.ts` и не поддерживает Turbopack — а `next dev` в этом проекте работает на Turbopack (см. `docker-compose.dev.yml`). Вместо урезанной/нестабильной интеграции под Turbopack — `disable: process.env.NODE_ENV !== "production"` в `withSerwistInit`: в dev service worker не собирается и не регистрируется вовсе (это и есть стандартная практика для PWA, не компромисс). Офлайн-поведение проверяется только на production-сборке (`npm run build && node .next/standalone/server.js`, либо `docker build --target runner`), не на `docker-compose.dev.yml`. Также обнаружилось, что сам `next build` в Next.js 16.3.0 по умолчанию собирает через Turbopack (не только `next dev`) — `package.json` `build`-скрипт зафиксирован как `next build --webpack`, иначе `@serwist/next` молча не подключается и `public/sw.js` не генерируется (см. Decision Log §15).

**`runtimeCaching` в `src/app/sw.ts`:** `[coilApiNetworkOnly, ...defaultCache]` — порядок принципиален (в serwist/workbox побеждает первое совпадение). `coilApiNetworkOnly` — единственное кастомное правило проекта, `NetworkOnly` без единого cache-фоллбэка для `GET /api/coil/:id` (матчер — чистая функция `isCoilVerdictApiPath` в `src/lib/pwa/sw-rules.ts`, покрыта unit-тестом `tests/unit/sw-rules.test.ts`, поскольку сам `sw.ts` тестировать в vitest/jsdom без Cache/ServiceWorker API нельзя). Она стоит раньше общего правила `defaultCache` для `/api/*` — там `NetworkFirst` с кэш-фоллбэком, что для решения МОЖНО/СТОП недопустимо. `defaultCache` (штатный набор стратегий `@serwist/next/worker` под Next.js) закрывает всё остальное: app shell (JS/CSS/шрифты/иконки — `CacheFirst`/`StaleWhileRevalidate`) и HTML-навигацию (`/`, `/check`, `/coil/:id` — `NetworkFirst` с кэш-фоллбэком под именем кэша `pages`/`others`).

**Справочники (Color/Thickness/Manufacturer/Coating) — без отдельного публичного JSON API.** Изначальный план §9 предполагал отдельный кэшируемый эндпоинт для справочников. По факту его нет и не появилось: `/check` (Iteration 5) разрешает параметры накладной server-side и встраивает результат прямо в SSR HTML (`src/app/check/page.tsx`, `force-dynamic`), а не запрашивает их отдельно с клиента. Кэш HTML-навигации `/check` (через `defaultCache`) уже даёт офлайн-доступ к ранее открытой накладной без отдельного API — заводить JSON-эндпоинт специально под PWA-кэш ради данных, которые больше нигде не нужны как отдельный API, было бы архитектурой ради архитектуры (см. Decision Log §15).

**Что кэшируется (stale-while-revalidate, если не указано иное):**
- App shell — JS/CSS-бандлы, иконки, шрифты (стратегия `CacheFirst`, версионируются автоматически хешами в имени файла при каждой сборке).
- Справочники — ответы, отдающие `Color`/`Thickness`/`Manufacturer`/`Coating` (используются для расшифровки `/check`-параметров и построения UI офлайн).
- HTML-оболочка страниц `/`, `/check` — статическая часть разметки, без бизнес-данных внутри самого закэшированного HTML.

**Что НЕ кэшируется никогда (`NetworkOnly`, без fallback на кэш):**
- `GET /api/coil/:id` — данные рулона, используемые для итогового сравнения. Всегда live-запрос.
- Client-side fetch, вычисляющий вердикт МОЖНО/СТОП на странице `/coil/:id` (см. §2, «важное исключение») — использует `cache: 'no-store'` явно на уровне fetch, а не полагается только на отсутствие route в SW-конфиге, чтобы промежуточные HTTP-кэши браузера тоже не подставили старый ответ.
- **Сама HTML-страница `/coil/:id`** (не только API) — изначально план предполагал `NetworkFirst`-кэш для read-only карточки (нет активного требования), но по факту это отключено: `NetworkFirst` без прогретого кэша при первом визите не имеет запасного варианта на случай единичного сетевого сбоя, и это стало реальной причиной ошибки навигации на iOS Safari сразу после сканирования рулона (см. `isCoilPagePath` в `src/lib/pwa/sw-rules.ts`, Decision Log §15, запись от 2026-08-14). Офлайн-повторный просмотр уже открытой read-only карточки рулона больше не работает — сознательно принесено в жертву ради надёжности основного сценария «скан → вердикт».

При отсутствии сети на любом из этих двух путей экран сразу показывает «НЕТ СВЯЗИ — НЕ УДАЛОСЬ ПРОВЕРИТЬ РУЛОН — СТОП», без попытки подставить старые данные, даже если этот рулон уже открывался раньше на этом телефоне.

Это прямая реализация раздела 32 ТЗ и снимает исходное противоречие «офлайн vs fail closed»: офлайн разрешён для UI и данных накладной, запрещён для решения по рулону — причём это разделение проведено не только на уровне «какой API-роут кэшируется», но и на уровне того, где физически вычисляется вердикт (§2), чтобы кэш HTML-оболочки не мог случайно унести в себе устаревшее решение.

**Статус проверки (честно, по аналогии с §10).** Проверено: логика правила `isCoilVerdictApiPath` (unit-тест), генерация `public/sw.js` через `next build --webpack` с правильным порядком `runtimeCaching` (правило для `/api/coil/` действительно стоит первым — проверено чтением собранного бандла), раздача `sw.js`/`manifest.webmanifest`/иконок и заголовков (`Cache-Control: no-store` на `/api/coil/:id`) из реального production Docker-образа (`docker build --target runner` + полный прогон `entrypoint.sh` против одноразовой БД). **Не проверено — открытый пробел:** реальное поведение service worker в браузере (регистрация, фактическое попадание HTML/assets в Cache Storage, поведение при физическом отключении сети через DevTools или авиарежим телефона) — в среде разработки нет браузерной автоматизации, только curl/Docker-уровень. Требует ручной проверки на реальном устройстве, как и пункт 17 чек-листа раздела 39 в §10 — это разные, не дублирующие друг друга пробелы (тот про камеру, этот про офлайн-кэш).

`manifest.json` — иконки, `display: standalone`. Подсказка «Добавить на главный экран» — не критична, опциональна.

## 10. QR-сканер

**Выбрана `html5-qrcode`** (движок ZXing) — с 2026-08-14, заменяет `qr-scanner` (nimiq). Причина замены не гипотетическая, а подтверждённая реальным устройством: см. Decision Log §15, запись от 2026-08-14.

**Статус проверки на реальном устройстве.** Первая библиотека (`qr-scanner`) была реально проверена на iPhone при закрытии более поздней итерации — и именно эта проверка вскрыла проблему (превью с камеры показывается, декодирование не срабатывает никогда). Замена на `html5-qrcode` **пока не проверена на реальном устройстве** — решение принято на основании (а) точного совпадения симптома с задокументированными открытыми issues в репозитории `nimiq/qr-scanner` (#33, #58, #121 — то же самое: работает превью, нет ошибок в консоли, декодирование не срабатывает), (б) исключения тривиальной причины (атрибуты `playsinline`/`muted` на `<video>` уже были на месте до замены — не в этом дело), (в) `html5-qrcode` использует тот же движок ZXing, который и так был заранее заложен в этом документе как план Б при проблемах с точностью распознавания (см. решение №7 в реестре §14 — тогда это называлось `zxing-wasm`, `html5-qrcode` даёт тот же движок в более готовой обёртке, не только декодер, но и управление камерой/permissions).

- **Проверено (автоматическими тестами, без реальной камеры):** та же логика, что и раньше — единственное срабатывание на кадр (`tests/unit/QrScannerView.test.tsx`, мок библиотеки под новый API), отклонение постороннего/чужого QR без остановки сканирования (раздел 8 ТЗ, пункт 9 чек-листа раздела 39), корректный запуск/остановка/очистка сканера при монтировании/размонтировании (`start()`/`stop()`/`clear()` — асинхронные в `html5-qrcode`, в отличие от синхронных в `qr-scanner`, тесты это учитывают).
- **НЕ проверено — требует ручной проверки на том самом iPhone, где не работал `qr-scanner`, прежде чем считать замену подтверждённой:** реальное декодирование QR через `html5-qrcode` на iOS Safari/Chrome-на-iOS; поведение на Android (`qr-scanner` там работал, регрессии не ожидается, но не проверено явно).

Компромисс при переходе: `html5-qrcode` не декодирует в Web Worker (в отличие от `qr-scanner`) — обработка кадров идёт в основном потоке с настраиваемым `fps` (используется `fps: 10`). Для этого приложения (сканирование одного QR за раз, не поток данных) это не создаёт заметных проблем с отзывчивостью UI на практике у большинства пользователей библиотеки, но это осознанный откат от изначального требования «не блокировать UI-поток» — принят ради того, чтобы сканер вообще работал на iOS, а не как решение без цены.

Валидация распознанного контента сканером — принимается только `/coil/:id`-паттерн собственного домена (`src/lib/worker/scan-url.ts`, функция `parseCoilScanUrl`) и, симметрично, только `/check`-паттерн для сканера накладной (`parseCheckScanUrl`); любой посторонний текст/URL/чужой домен — явно отклоняются с сообщением, сканирование продолжается (раздел 8 ТЗ). Защита от повторного срабатывания одного кадра — не таймер-дебаунс, а флаг «уже обработано» в `QrScannerView`: как только валидный QR подтверждён, сканер немедленно останавливается (`scanner.stop()`) и `onScan` вызывается ровно один раз за монтирование компонента.

### 10.1 Печать паспорта рулона (Iteration 8) ⚠️ реализовано и проверено декодированием; печать на реальном принтере — ОТКРЫТА

**Генерация:** `qrcode@1.5.4`, серверный SVG (`src/lib/qr/coil-passport.ts`, функция `generateCoilQrSvg`), встраивается прямо в SSR HTML страницы паспорта. `errorCorrectionLevel: "H"` — печатная этикетка в цеху подвержена загрязнению/бликам/заломам сильнее, чем экран телефона в контролируемых условиях сканирования накладной.

**Что кодирует QR:** `buildCoilPublicUrl(NEXT_PUBLIC_APP_URL, coil.id)` — абсолютная ссылка на `/coil/:id`, симметричная тому, что принимает `parseCoilScanUrl` (§10, выше) — то есть напечатанный QR читается тем же кодом сканера, что и любой другой `/coil/:id`, никакой отдельной ветки логики для «печатных» QR нет. Домен берётся из валидированного `NEXT_PUBLIC_APP_URL` (`src/lib/config.ts`), не из `Host`-заголовка запроса на момент печати — детерминированность важнее удобства открытия со случайного адреса.

**Страница печати — `/admin/coils/[id]/print`, под admin-авторизацией**, не отдельная публичная страница (см. Decision Log §15 за обоснованием выбора). Ссылка «Печать» — рядом с «Открыть» в списке рулонов (`CoilsManager`). `window.print()` (клиентская кнопка `PrintButton`) + `@media print` в `globals.css` (класс `.no-print` скрывает admin-навигацию и саму кнопку при печати). Серверный PDF не потребовался — одной печатной карточки достаточно.

**Статус проверки (честно, по аналогии с §9/§10).** Проверено — **настоящий round-trip, не мок:** unit-тест `tests/unit/coil-passport.test.ts` кодирует ссылку через `qrcode` → PNG (тот же движок кодирования модулей, что и у SVG в паспорте, отличается только рендерер) → `pngjs` читает пиксели → `jsqr` раскодирует изображение обратно в текст → результат сверяется с исходной ссылкой и дополнительно прогоняется через `parseCoilScanUrl` — тот же валидатор, которым реальный сканер на `/scan/coil` будет проверять QR при сканировании. Также вручную открыта `/admin/coils/[id]/print` в dev-стеке под реальной admin-сессией — SVG отдаётся корректно, визуально проверен сгенерированный QR. **Не проверено — открытый пробел:** физическая печать на настоящем принтере и считывание получившейся бумажной этикетки обычной камерой телефона (может выявить то, чего нет в цифровом round-trip — DPI принтера, размер этикетки, качество тонера/бумаги, блики) — тот же класс пробела, что и реальная камера в §10 и реальный офлайн-режим в §9, независимая, не дублирующая проверка.

## 11. Деплой на Timeweb Cloud

Кратко здесь, подробно — `DEPLOYMENT.md`. Один Docker-контейнер (`next build` standalone output) + управляемый PostgreSQL Timeweb. **Dev и prod — физически разные инстансы БД** с раздельными `DATABASE_URL` (нет фичи веток БД, как в Neon — явно зафиксировано с Iteration 1, не как техдолг «на потом»). Миграции — `prisma migrate deploy` отдельным шагом перед стартом контейнера. HTTPS — через reverse-proxy/сертификат Timeweb перед контейнером.

### 11.1 Механизм защиты от смешения dev/prod (не только декларация, а рабочая проверка)

Урок из инцидента на Neon: одной договорённости «использовать разные `DATABASE_URL`» недостаточно — переменная окружения может быть скопирована не туда, деплой-скрипт может унаследовать не то значение, разработчик может по ошибке запустить миграцию с локально выставленным prod-URL. Раз Timeweb не даёт веток БД, которые раньше подстраховывали от этого технически, изоляция строится на **двух независимых уровнях**, а не на одном:

**Уровень 1 — физический.** Dev и prod — это два отдельных managed PostgreSQL-инстанса Timeweb (разный хост, разные учётные данные), не одна БД с разными именами схем и не одна БД с разными ролями. Разные инстансы означают, что скомпрометированный/перепутанный креды одного окружения физически не имеют доступа к данным другого — это не переключаемый флаг, а разные сетевые адреса.

**Уровень 2 — активная проверка при старте (`EnvironmentGuard`, см. §4.6).** Этого недостаточно самого по себе — нужна проверка, которая ловит человеческую ошибку до того, как она нанесёт вред:

1. При первичной подготовке каждого инстанса (dev и prod) вручную выполняется одноразовая seed-операция, которая создаёт единственную строку в `EnvironmentGuard` со значением `env = "development"` либо `env = "production"` — это делается один раз человеком при создании инстанса, не автоматически и не выводится из URL/имени.
2. Приложение получает **отдельную** переменную окружения `APP_ENV` (`development` | `production`) при каждом запуске — независимо от `NODE_ENV`, который управляет поведением сборки Next.js, а не тем, к какой физической БД можно подключаться.
3. `src/lib/config.ts` при старте процесса (до `prisma migrate deploy` и до приёма любого трафика) читает `EnvironmentGuard.env` из БД, на которую указывает текущий `DATABASE_URL`, и сравнивает с `APP_ENV`. **При несовпадении или отсутствии записи — процесс немедленно завершается с явной ошибкой**, миграции не запускаются, сервер не поднимается.

Практический эффект: если кто-то по ошибке запустит prod-контейнер (`APP_ENV=production`) с dev-строкой подключения (где `EnvironmentGuard.env = "development"`) — или наоборот, локальный dev-процесс укажет на prod `DATABASE_URL` — приложение откажется стартовать вместо того, чтобы молча начать читать/писать не в ту базу. Это и есть механизм, устраняющий зависимость от «переключения окружения» как единственной защиты — именно то, чего не хватало в инциденте с Neon.

Дополнительно: секреты dev и prod хранятся в разных местах (разные `.env`-файлы/секрет-хранилища деплой-платформы), никогда не в одном файле с переключением через комментирование строк.

### 2026-08-12 — Известный dev-only баг роутинга Next.js `16.3.0`: не понижаем версию, живём с ним

**Контекст.** При сквозной проверке Iteration 3 обнаружено: в dev-режиме (`next dev`, воспроизведено и под Turbopack, и под `--webpack`) маршруты вида `/api/admin/{ресурс}/[id]/{действие}/route.ts` (`deactivate`/`restore` у `colors`/`thicknesses`/`manufacturers`/`coatings`/`coils`) иногда отвечают 404 вместо ожидаемого статуса — при том, что `[id]/route.ts` без дополнительного статического сегмента работает стабильно. Первая версия этой находки (см. DEPLOYMENT.md, Iteration 2) ошибочно приписывала причину устаревшему `app-next-cache` volume — это было неверно, `docker volume rm` иногда «помогал» случайно. Локализовано экспериментально (изолированные тестовые маршруты той же формы): причина — сам dev-сервер Next.js 16.3.0 некорректно регистрирует маршруты при 5+ параллельных ресурсах с одинаковой вложенной формой `[id]/статический-сегмент/route.ts`; не зависит от кэша, бандлера или содержимого хендлера.

**Решение.** Версию Next.js не понижаем и API не перестраиваем в обход паттерна. **Production не затронут** — явно проверено (`next build && next start`): те же URL, что 404-или в dev, корректно отдают 200/410/404 в собранном приложении. Раз это дефект исключительно dev-сервера, а не приложения, самый дешёвый правильный ответ — знать о нём и не тратить время на поиск несуществующего бага в коде.

**Причина.** Понижение Next.js ради dev-only бага в фреймворке несоразмерно (пришлось бы also downgrade React/next-config API и заново всё проверять), а перестройка API (например, слияние `deactivate`/`restore` в `PATCH`) — реальная архитектурная правка ради обхода временной проблемы одной версии инструмента, а не потому что так лучше по существу.

**Когда пересматривать.** При обновлении Next.js на следующий minor/patch — проверить, воспроизводится ли баг ещё (см. DEPLOYMENT.md за точным сценарием воспроизведения); если да, оставить эту заметку, если нет — удалить обе заметки (эту и в DEPLOYMENT.md) как неактуальные.

### 2026-08-12 — Excel-библиотека: `exceljs`, не `xlsx` (SheetJS), вопреки первоначальному плану

**Контекст.** В разделе 12 первого архитектурного прохода в качестве кандидата был указан `xlsx` (SheetJS). На практике: npm-пакет `xlsx` не обновлялся с марта 2022 (последняя версия `0.18.5`) — SheetJS перешли на распространение свежих версий через собственный CDN отдельно от npm из-за спора с реестром, и патчи безопасности (были известные ReDoS/prototype-pollution issues) в npm-версию с тех пор не бэкпортировались. Для модуля, разбирающего **загружаемые пользователем файлы** (admin, но всё равно недоверенный ввод) — это неподходящий профиль риска.

**Решение.** Использован `exceljs@4.4.0` — активно поддерживаемый, публикуется в npm обычным образом, полноценно читает и пишет `.xlsx` (нужно для парсинга загрузки и генерации шаблона).

**Причина.** Секьюрити-профиль важнее для этого модуля, чем для большинства зависимостей — единственная точка, где сервер разбирает произвольный бинарный файл, загруженный человеком.

**Остаточный риск (принят, не блокирует).** `exceljs` тянет транзitivную умеренную уязвимость в `uuid` (`GHSA-w5hq-g745-h8pq`, missing bounds check при передаче кастомного `buf`) — `npm audit fix --force` предлагает откатить `exceljs` до `3.4.0` (хуже: старее и без части фиксов). `uuid` используется `exceljs` для внутренних нужд (генерация ID для XLSX-примитивов), не получает напрямую байты из содержимого загруженного файла — эксплуатация через наш attack surface маловероятна. Принято как есть; проверить при следующем обновлении `exceljs`, не появилась ли версия без этой транзитивной зависимости.

**Когда пересматривать.** Если `exceljs` перестанет поддерживаться, или появится альтернатива без транзитивных уязвимостей — не как рутинный апдейт.

### 2026-08-12 — `@serwist/next` не поддерживает Turbopack: service worker собирается только в production, `next build` форсирует webpack

**Контекст.** При подключении `@serwist/next` (Iteration 7) выяснилось: пакет интегрируется через `webpack()`-хук `next.config.ts` и явно предупреждает при запуске под Turbopack, что не поддерживает его (есть экспериментальный `@serwist/turbopack` и отдельный «configurator mode», ни то ни другое не пробовалось — см. «Когда пересматривать»). У проекта `next dev` работает на Turbopack (`turbopack: {...}` в `next.config.ts`, унаследовано с Iteration 1). Отдельно обнаружилось, что и `next build` в Next.js 16.3.0 по умолчанию тоже собирает через Turbopack (не только `next dev`) — первый прогон `npm run build` завершился без ошибок, но `public/sw.js` тихо не появился, потому что webpack-плагин serwist просто не вызывался.

**Решение.** Два независимых, но связанных решения: (1) `withSerwistInit({ disable: process.env.NODE_ENV !== "production", ... })` — в dev service worker не собирается и не регистрируется вообще, никакого урезанного/нестабильного поведения под Turbopack; (2) `package.json` `build`-скрипт зафиксирован как `next build --webpack`, чтобы production-сборка гарантированно шла через webpack и `@serwist/next` реально подключался. `next dev` (Docker dev-стек) остался на Turbopack без изменений — офлайн-функциональность не тестируется в dev-режиме в принципе, это ожидаемое ограничение, а не баг.

**Причина.** Отключение SW в dev — стандартная, а не компромиссная практика (SW, кэширующий HMA-сборки, только мешал бы разработке); `--webpack` для build — минимальное вмешательство, ограниченное одним CLI-флагом, не требующее миграции на experimental Turbopack-интеграцию serwist ради непроверенной экономии времени сборки.

**Когда пересматривать.** Если `@serwist/turbopack` или «configurator mode» станут документированно стабильными для Next.js App Router — можно вернуть `next build` на Turbopack по умолчанию и убрать флаг; смотреть https://github.com/serwist/serwist/issues/54.

### 2026-08-12 — `docker/Dockerfile`: production-образ не мог запустить миграции (баг найден при проверке Iteration 7, не связан с PWA)

**Контекст.** При сквозной проверке production-образа (`docker build --target runner` + реальный `entrypoint.sh` против одноразовой БД — впервые проверено сквозным прогоном, раньше Iteration 9 не начиналась) `prisma migrate deploy` падал с `ENOENT: .../node_modules/.bin/prisma_schema_build_bg.wasm`. Причина: `COPY --from=builder /app/node_modules/.bin/prisma ./node_modules/.bin/prisma` копировал **один файл**, который в builder-стадии является symlink на `../prisma/build/index.js` — Docker BuildKit при копировании одиночного symlink-файла (в отличие от копирования целого каталога) разыменовывает его в обычный файл. Скрипт после этого исполняется как будто лежит прямо в `.bin/` и не находит соседний `.wasm` по относительному пути, который в реальности лежит в `prisma/build/`. После обхода этого (прямой вызов `node node_modules/prisma/build/index.js`) вскрылась вторая, независимая проблема: CLI Prisma 6.19.3 транзитивно зависит от пакета `effect`, которого не было в runner-образе — там точечно копировались только `prisma`/`@prisma`/`.bin/prisma`, без их транзитивных зависимостей, поднятых npm в корень `node_modules`.

**Решение.** Добавлена отдельная стадия `prod-deps` (`npm ci --omit=dev` по тому же `package-lock.json`, без devDependencies) и её `node_modules` копируется в runner **целиком одной командой** (`COPY --from=prod-deps /app/node_modules ./node_modules`) — вместо трёх точечных `COPY` отдельных подпапок/файлов. Копирование каталога целиком сохраняет symlink рабочим (в отличие от копирования одного файла) и гарантированно включает все транзитивные зависимости CLI, а не только те, что случайно пришли в голову ранее.

**Причина.** Точечное перечисление файлов для CLI-инструмента — хрупкий паттерн: он молча ломается при любом обновлении Prisma, добавляющем новую транзитивную зависимость, и это не поймать раньше первого реального прогона `prisma migrate deploy` в собранном образе (что и произошло — баг был в Dockerfile с момента, когда там появился production runner, но не был замечен, потому что Iteration 9 деплой ещё не начинался, а до этого никто не гонял `entrypoint.sh` целиком в контейнере).

**Причина, почему это не откладывается до Iteration 9.** Без этой правки production-образ детерминированно падает на старте — это не тонкая оптимизация «на потом», а сломанный entrypoint; оставлять DEVELOPMENT_PLAN.md с формально «готовой» Iteration 7 при заведомо неработающем production-контейнере было бы недобросовестной отчётностью.

**Остаточный компромисс.** `prod-deps` крупнее точечных COPY (полный граф production-зависимостей, а не три вручную выбранных пакета) — уже без devDependencies (`typescript`/`eslint`/`vitest`/…), но не минимизирован под то, что реально нужно только для `prisma migrate deploy`. Приемлемо для V1; если размер образа станет проблемой — оптимизировать в Iteration 9 вместе с остальной deploy-настройкой, не раньше.

**Когда пересматривать.** При обновлении Prisma до следующей минорной/мажорной версии — проверить, что `prisma migrate deploy` в собранном `runner`-образе всё ещё отрабатывает (не полагаться только на то, что `npm run build` прошёл — это НЕ проверяет entrypoint).

### 2026-08-14 — `entrypoint.sh` явно выставляет `HOSTNAME=0.0.0.0` перед стартом сервера

**Контекст.** Первый реальный деплой на Timeweb Cloud App Platform (Iteration 9): контейнер стабильно проходил `EnvironmentGuard`, применял миграции и логировал `✓ Ready` — но healthcheck платформы (даже упрощённый до `GET /api/health`, вообще без обращения к БД) никогда не проходил, контейнер бесконечно перезапускался по таймауту. Разгадка была в самом баннере запуска Next.js: `- Network: http://<container-id>:3000` вместо ожидаемого `0.0.0.0`. Сгенерированный `.next/standalone/server.js` слушает на `process.env.HOSTNAME || '0.0.0.0'` — а `sh` (ash/dash в `node:24-alpine`), под которым `entrypoint.sh` запускает `node server.js`, автоматически экспортирует `HOSTNAME` равным имени хоста контейнера (в Docker это container ID). Из-за этого автоэкспорта переменная никогда не оказывается пустой, дефолт `'0.0.0.0'` не срабатывает, и сервер слушает адрес, не принимающий подключения снаружи контейнера — при том что сам процесс изнутри выглядит полностью рабочим (главная ловушка: логи не показывают вообще никакой ошибки).

**Решение.** `docker/entrypoint.sh`: `export HOSTNAME=0.0.0.0` непосредственно перед `exec node server.js` — явное переопределение побеждает автоэкспорт shell'а, поскольку выполняется позже в том же скрипте. Проверено локально прогоном собранного `runner`-образа: без фикса `curl` до контейнера снаружи не отвечает вовсе (не 4xx/5xx, а обрыв соединения), с фиксом — `200` на `/api/health` и `/api/health/ready`.

**Причина.** Это особенность связки Next.js standalone + POSIX-shell в Docker, а не что-то специфичное для Timeweb — тот же баг проявился бы на любой платформе, которая делает healthcheck HTTP-запросом снаружи контейнера (а не `docker exec` изнутри), и остался бы незамеченным в средах, где healthcheck не настроен вовсе (поэтому не всплыло раньше — до Iteration 9 контейнер запускался только через `docker run`/`docker compose` без внешнего healthcheck-пробера).

**Когда пересматривать.** Не требуется — это не временный обход, а корректная фиксация адреса прослушивания, которая должна быть частью любого production-запуска standalone-сборки Next.js в Docker.

### 2026-08-14 — `Dockerfile` (runner) устанавливает `curl`

**Контекст.** После фикса `HOSTNAME` (запись выше) деплой на Timeweb Cloud App Platform всё ещё падал по таймауту healthcheck, а прямое обращение к техническому домену отдавало `ERR_SSL_PROTOCOL_ERROR`. Локальная проверка `docker run -p 3001:3000` + `curl` **с хост-машины** (то есть максимально точное воспроизведение внешнего HTTP-healthcheck, какое только можно сделать локально) проходила чисто — 200 на оба health-эндпоинта. Расхождение с реальным деплоем объяснилось ответом поддержки Timeweb: их healthcheck выполняется как `docker exec <container> curl ...` **внутри** контейнера, а не внешним HTTP-запросом. Базовый образ `node:24-alpine` не включает `curl` — команда просто не могла выполниться (`curl: not found`), и деплой не мог завершиться успехом ни при каких обстоятельствах, независимо от того, насколько здоров сам процесс Next.js.

**Решение.** `RUN apk add --no-cache curl` в `runner`-стадии `Dockerfile`, рядом с созданием непривилегированного пользователя. Проверено локально через точное воспроизведение механизма Timeweb — `docker exec <container> curl http://localhost:3000/api/health` — 200 после добавления пакета, без пакета команда не выполняется вовсе.

**Причина.** Локальное воспроизведение (`docker run -p` + внешний `curl`) — стандартный и в целом правильный способ проверки, но он неявно предполагает конкретный механизм healthcheck (внешний HTTP-проб). Когда платформа использует другой механизм (`exec` внутрь контейнера), совпадение результата локальной и реальной проверки не гарантировано — этот пробел закрылся не более тщательным тестированием той же гипотезы, а прямым вопросом в поддержку платформы о том, как именно устроена их проверка.

**Когда пересматривать.** Не требуется — `curl` в образе не создаёт заметного оверхеда по размеру и является общеупотребимой утилитой для диагностики самого контейнера при необходимости.

### 2026-08-13 — `Dockerfile` перенесён в корень репозитория (был `docker/Dockerfile`)

**Контекст.** При настройке деплоя на Timeweb Cloud App Platform (Iteration 9) выяснилось: единственное поле, которым App Platform определяет и расположение `Dockerfile`, и build context для сборки — «Путь до директории проекта» (подсказка платформы: «Путь относительно корня репозитория к папке с файлами `package.json` или `Dockerfile`… Оставьте пустым, если файлы находятся в корне репозитория»). Платформа не разделяет «где лежит Dockerfile» и «что считать build context» — это одно и то же поле, то есть предполагается монорепо-паттерн, где обе вещи лежат в одной указанной директории. У нашего `Dockerfile` (тогда — `docker/Dockerfile`) все `COPY`-инструкции написаны в расчёте на **build context = корень репозитория** (например, `COPY docker/entrypoint.sh ./entrypoint.sh`, `COPY prisma ./prisma`) — если бы полю указали `docker`, платформа использовала бы `docker/` и как расположение Dockerfile, и как context, и сборка сломалась бы (не нашла бы `package.json`, `prisma/`, и т.д. по путям, ожидающим корень).

**Решение.** `Dockerfile` перенесён (`git mv`) из `docker/Dockerfile` в `Dockerfile` в корне репозитория; `docker/entrypoint.sh` остался на месте (Dockerfile ссылается на него по пути `docker/entrypoint.sh` — этот путь не менялся, так как build context как был, так и остаётся корнем). Поле «Путь до директории проекта» в Timeweb оставлено пустым. `docker-compose.dev.yml` (`dockerfile:`) обновлён на новый путь.

**Причина.** Минимальное по объёму изменение (перемещение одного файла, без правки его содержимого), которое делает репозиторий совместимым с ограничением конкретной платформы, вместо того чтобы городить обходной путь (например, отдельный урезанный Dockerfile специально под Timeweb, дублирующий логику).

**Когда пересматривать.** Не требуется — размещение `Dockerfile` в корне репозитория само по себе более стандартно (так делает большинство инструментов по умолчанию), это не временный компромисс.

### 2026-08-14 — QR-сканер переведён с `qr-scanner` на `html5-qrcode`

**Контекст.** На реальном iPhone (Safari и Chrome-на-iOS, где движок тот же WebKit) сканер на `/scan/coil` и `/scan/invoice` включал камеру, показывал живое превью — и ни разу не распознавал QR-код. Проверка `<video>`-атрибутов (`playsinline`, `muted`) ничего не дала — оба уже стояли в разметке (`QrScannerView.tsx`, ещё до этой правки). Поиск подтвердил: это задокументированная, годами открытая проблема самой библиотеки `qr-scanner` (nimiq) — issues #33, #58, #121 в её репозитории описывают ровно тот же симптом (превью работает, ошибок в консоли нет, декодирование не срабатывает никогда), специфично для iOS Safari/WebKit. Библиотека не выпускала релизов с ноября 2022.

**Решение.** Заменена на `html5-qrcode@2.3.8` (движок ZXing). Публичный API `QrScannerView` не изменился (`validate`/`onScan`/`onCancel`/`instructions`) — переписана только внутренняя реализация: вместо `<video>`-элемента с ref — `<div>`-контейнер с `id` (генерируется через `useId()`, двоеточия заменены на дефисы — `html5-qrcode` использует id как CSS-селектор внутри себя, а неэкранированное двоеточие в селекторе некорректно), `Html5Qrcode(elementId).start(...)` вместо `new QrScanner(video, ...).start()`. `start()`/`stop()`/`clear()` асинхронные (в `qr-scanner` были синхронными) — учтено в cleanup-функции эффекта и в unit-тестах.

**Причина.** Симптом воспроизводится не из-за неправильной настройки на нашей стороне (атрибуты видео были верны), а из-за самой библиотеки — дальнейшая отладка `qr-scanner` бессмысленна, это её собственный многолетний открытый баг. `html5-qrcode` использует тот же движок ZXing, который заранее был заложен в этом документе как запасной вариант (изначально под именем `zxing-wasm`, до реальной проверки на устройстве) — решение не экспромт, а реализация уже предусмотренного плана Б, только в оболочке с готовым управлением камерой вместо голого WASM-декодера.

**Остаточный компромисс.** `html5-qrcode` не использует Web Worker для декодирования (в отличие от `qr-scanner`) — обработка кадров идёт в основном потоке JS с частотой `fps: 10`. Это осознанно принятая цена, не полностью бесплатная замена: для однократного сканирования (не потоковой обработки) заметных проблем с отзывчивостью UI не ожидается, но это открытая позиция, не проверенная на слабых Android-устройствах.

**Когда пересматривать.** После подтверждения на реальном iPhone (том самом, где не работал `qr-scanner`) — если проблема не исчезла, значит гипотеза о причине была неверна, и нужно смотреть глубже (например, реальную консоль устройства через Safari Web Inspector с Mac, а не гадать по паттерну известных issues другой библиотеки).

### 2026-08-14 — Навигация на `/coil/:id` сразу после скана падала на iOS Safari («This page couldn't load»); `/coil/:id` переведена на `NetworkOnly`, исправлена гонка при остановке камеры

**Контекст.** После перехода на `html5-qrcode` (запись выше) обнаружился новый симптом: первая попытка открыть `/coil/:id` сразу после успешного скана на `/scan/coil` на iOS Safari иногда давала браузерную ошибку «This page couldn't load» (не наш React error boundary — сбой на уровне самого сетевого запроса/навигации); повторная загрузка (Reload) той же страницы всегда проходила нормально.

**Расследование нашло два независимых, накладывающихся друг на друга источника.**

1. **Гонка при остановке камеры в `QrScannerView`.** Callback успешного декодирования вызывал `scanner.stop().then(() => scanner.clear())` **не дожидаясь** завершения (fire-and-forget) и сразу синхронно звал `onScan(...)`, что в вызывающем коде (`ScanCoilPage`) немедленно делает `router.push('/coil/'+id)`. То есть навигация стартовала, пока браузер ещё физически не закончил останавливать активный `MediaStream` камеры — правдоподобный источник нестабильности сетевого запроса конкретно на WebKit/iOS, где ресурсы камеры и сети более тесно связаны, чем в Chromium. У старой библиотеки (`qr-scanner`) `stop()` был синхронным, поэтому эта гонка физически не могла возникать раньше — она появилась именно вместе с переходом на асинхронный API `html5-qrcode`, независимо от того, была ли она единственной причиной сбоя.
2. **`NetworkFirst` без кэш-фоллбэка на первый визит.** Собранный `sw.js` показал: клиентская навигация Next.js (`router.push`) на ранее не посещённый URL уходит RSC-фетчем, который попадает под правило `NetworkFirst` из `defaultCache` (`@serwist/next/worker`), без `networkTimeoutSeconds` (то есть без принудительного разрыва по таймауту — только настоящий сбой самого `fetch()` триггерит fallback). Для страницы, которую браузер открывает первый раз в этой сессии, кэша под fallback ещё нет — если сетевой запрос по любой причине оборвётся (в том числе из-за пункта 1 выше, или из-за собственных гонок Service Worker на WebKit при активации/`clients.claim()`), `NetworkFirst` не может ничем подстраховать и отдаёт ошибку сети напрямую в браузер — это и есть Safari-шная «This page couldn't load», не что-то, что можно перехватить в React.

**Решение.** Оба источника устранены: (а) `QrScannerView` теперь дожидается `stop()`+`clear()` (`.finally(() => onScan(...))`) прежде чем вызывать `onScan` и, соответственно, до начала навигации; (б) `src/app/sw.ts` — добавлено отдельное `NetworkOnly`-правило для самой HTML-страницы `/coil/:id` (`isCoilPagePath`, `src/lib/pwa/sw-rules.ts`), а не только для API `/api/coil/:id`, которое уже было `NetworkOnly` — так первая навигация на `/coil/:id` больше не проходит через `NetworkFirst` вообще, значит и «пустой кэш при сбое» для неё больше не сценарий.

**Причина.** Оба фикса независимо обоснованы и не являются взаимоисключающими рабочими гипотезами «на всякий случай» — каждый устраняет конкретный, объяснимый механизм сбоя. Более простая правка (дождаться `stop()`) сделана в первую очередь как объективно более корректный код независимо от того, была ли она единственной причиной; правка SW дополнительно убирает саму возможность «пустой кэш → голая ошибка сети» для самого частого пути в приложении (после каждого скана рулона), даже если гонка с камерой была не единственным триггером.

**Остаточный компромисс.** Офлайн-повторный просмотр уже однажды открытой read-only карточки `/coil/:id` (без активного требования) больше не работает — та часть офлайн-функциональности из ARCHITECTURE.md §9 была не критичной («опционально», не часть основного сценария) и сознательно принесена в жертву ради надёжности основного потока «скан рулона → вердикт», который выполняется на несколько порядков чаще.

**Когда пересматривать.** После подтверждения пользователем на реальном iPhone, что навигация на `/coil/:id` после скана больше не падает — оба фикса реализованы и покрыты unit-тестами, но ни один не проверен на самом устройстве, где воспроизводилась проблема (нет доступа к браузерной автоматизации в среде разработки — тот же класс пробела, что и во всех предыдущих записях этого журнала про реальные устройства).
