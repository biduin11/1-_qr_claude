# EXCEL_IMPORT.md — массовый импорт рулонов

## Формат файла

`.xlsx`, лист `Import`, колонки (первая строка — заголовки, ровно эти имена):

| ral | thickness | manufacturer | coating |
|---|---|---|---|
| 7024 | 0.50 | uzbekistan | viking |
| 9003 | 0.45 | severstal | matte |

- Одна строка = один физический рулон. Повторяющиеся строки допустимы (несколько рулонов с одинаковыми характеристиками — норма, у каждого будет свой ID и QR, раздел 24 ТЗ).
- Формат значений в колонках — тот же, что и для параметров `/check` (см. QR_CONTRACT.md): `ral` — только цифры, `thickness` — число с точкой, `manufacturer`/`coating` — коды строчными буквами либо зарегистрированные alias-варианты.
- Пустых строк внутри диапазона данных быть не должно — первая полностью пустая строка считается концом данных.

## Лист `Reference`

Второй лист файла-шаблона, генерируется автоматически из текущего состояния справочников на момент скачивания шаблона (`GET /api/admin/export/excel-template`), только для чтения — справочная информация для заполняющего файл, не часть импортируемых данных:

| Тип | Код | Название |
|---|---|---|
| ral | 7024 | RAL 7024 |
| ral | 9003 | RAL 9003 |
| thickness | 0.50 | 0,50 мм |
| manufacturer | uzbekistan | Узбекистан |
| manufacturer | severstal | Северсталь |
| coating | viking | Viking |

Так как справочники могут измениться, шаблон стоит скачивать заново перед каждым крупным импортом, а не переиспользовать старый файл.

## Поток импорта (admin UI) — где именно хранятся данные между шагами

Между «показать превью» и «нажать подтвердить» **сервер ничего не хранит** — ни временную таблицу, ни кэш с токеном/TTL. Единственный держатель провалидированных строк в этот промежуток — открытая вкладка браузера admin'а (обычное состояние React-компонента страницы импорта). Это осознанное решение (не то, что «уточнится в процессе реализации») — подробное обоснование в ARCHITECTURE.md §7.

1. **Загрузка** — admin выбирает `.xlsx`-файл.
2. **Парсинг** — сервер читает лист `Import`, построчно. Ничего не сохраняет на сервере.
3. **Нормализация** — те же правила, что для `/check` (`material-normalization.ts`): форматная для `ral`/`thickness`, alias-lookup для `manufacturer`/`coating`.
4. **Валидация (первый раз)** — для каждой строки проверяется: все 4 значения присутствуют, `ral` существует и активен в справочнике, `thickness` существует и активен, `manufacturer` существует и активен, `coating` существует и активен.
5. **Превью** — ответ сервера содержит итоги («Всего строк: N, корректных: K, с ошибками: M») + таблицу ошибок по номерам строк (например «Строка 7: неизвестное покрытие rooftop_barhat») + сами провалидированные строки с разрешёнными ссылками на справочники. Сервер после отправки этого ответа не помнит про импорт — состояние живёт только в браузере, пока открыта страница. **Если admin перезагрузит страницу или закроет вкладку до подтверждения — превью теряется, нужно загрузить файл заново.** Это ожидаемое поведение, не баг.
6. **Подтверждение** — admin нажимает «Импортировать». Браузер отправляет **тот же набор строк**, что показывал в превью, обратно на сервер. Кнопка блокируется сразу после первого клика (защита от повторного нажатия/двойного сабмита в рамках одного клика), запрос дополнительно идёт с идемпотентным ключом (защита от повторной отправки того же запроса сетью/браузером).
7. **Валидация (второй раз, на сервере)** — сервер не доверяет присланным строкам просто потому, что они «уже проверены на превью»: он заново проверяет, что каждая ссылка на справочник (`ral`/`thickness`/`manufacturer`/`coating`) всё ещё существует и активна **на момент confirm**, а не на момент parse. Это закрывает разрыв во времени между превью и подтверждением (кто-то мог деактивировать значение справочника, пока admin смотрел на экран превью).
8. **Создание** — только строки, прошедшие вторую валидацию, создают `Coil`-записи, одной транзакцией. Строки, не прошедшие повторную проверку, попадают в `skipped`, не откатывая остальной импорт.
9. **Отчёт** — «Импортировано: N, пропущено: M» (пропущенные — строки с ошибками либо из первой, либо из второй валидации; невалидная строка никогда не создаёт `Coil`, при любом раскладе).

## Ограничения

- Максимум строк за один импорт: **5000** (защита от исчерпания памяти при парсинге на сервере). При превышении — понятная ошибка до начала парсинга по содержимому, импорт не выполняется.
- Импортируются **только** строки, прошедшие валидацию целиком. Частично заполненная строка (например, есть `ral`, но пустой `coating`) — вся строка невалидна, не импортируется по частям.
- Импорт не проверяет и не блокирует по дубликатам между строками — одинаковые строки создают несколько разных `Coil` (ожидаемое поведение, не ошибка).

## Что импорт НЕ делает

- Не изменяет существующие справочники — если в файле встречается код производителя, которого нет в справочнике, это ошибка валидации строки, а не повод создать новую запись справочника автоматически. Новые значения справочников admin добавляет отдельно, осознанно, до импорта.
- Не удаляет и не деактивирует существующие `Coil` — только создаёт новые.
- Не поддерживает обновление существующих рулонов через тот же файл (это не CSV-sync, а разовое добавление).
